## 1. The goal in one paragraph

We predict the **MOS** (the 1–5 rating a tester gives a video session) from the other columns of the
PoQeMoN dataset: 1,543 sessions watched by 181 testers. We compare several models (kNN, SVC, decision
tree, XGBoost), tune them with grid search, and evaluate them properly on data they have never seen.

## 3. What changed compared with our first notebook, and why

Our first notebook worked, but it had problems the guidelines explicitly penalise, plus a few
methodological issues an examiner would likely spot.

| Before | Now | Why |
|---|---|---|
| The same split / grid search / evaluation code was copied 4–5 times, cells had been run out of order | One clean pipeline, runs top to bottom | Guidelines: "code that runs without manual changes or hidden notebook state" |
| The "Key findings" cell was generic text ("look for skewed features…") | Real findings with numbers | Guidelines: explain what we observed and how it guided us |
| Random **60/20/20** train/validation/test split | **80/20** train/test, and **5-fold cross-validation** on the 80% for tuning | Uses more data for training, and CV gives a more stable comparison than one small validation set |
| Sessions of the same tester could be in both train and test | Split **by tester** (`StratifiedGroupKFold` on `user_id`) | Testers have 2–45 sessions each; we want to predict for *new* users (see §5) |
| `LabelEncoder` on phone model / OS version | **One-hot encoding** | Label encoding invents an order (e.g. "Nexus 4 < SM-G900F"), which distorts kNN/SVC distances |
| `StandardScaler` fitted once, before cross-validation | Scaling done **inside** a scikit-learn `Pipeline` | Otherwise statistics from the validation folds leak into training |
| Skewed columns used as-is | `log(1+x)` on buffering time/count, dropped frames, audio loss | A few extreme sessions were dominating kNN/SVC distances |
| Only accuracy | **Macro-F1** (used to pick models), accuracy, and **MAE** | 51% of sessions have MOS = 4, so "always predict 4" already gets 51% accuracy |
| No baseline | A "Dummy" model that always predicts the most frequent class | Shows how much the real models actually add |
| All columns used as features | Two experiments: **with** and **without** the `QoF_*` columns | See §4: this is the most important finding |

On the kNN/SVC side specifically, the logic is the same as before, but the grids are larger:
- kNN: `n_neighbors` 3–21, `weights` uniform/distance
- SVC: linear and RBF kernels, `C` 0.1–100, `gamma` for RBF

## 4. The most important finding: the `QoF_*` columns

According to the dataset README, `QoF_begin`, `QoF_shift`, `QoF_audio` and `QoF_video` are **user
feedback**: the tester's own 1–5 ratings of start-up, quality changes, audio and video. They are given in
the same questionnaire as the MOS.

- `QoF_audio` alone correlates **0.83** with MOS.
- A model that uses them is basically predicting "the overall rating" from "the partial ratings". In a real
  deployment you would not have them, because the whole point is to estimate QoE *without* asking the
  user.

So every experiment is run twice:
- **Objective features** (16 columns): player measurements, network, device, user profile. This is the
  realistic setting.
- **With feedback** (20 columns): the same plus the 4 `QoF_*` columns. This is an upper bound.

## 5. Why we split by tester

Each tester rated 2–45 sessions, and some testers are generous while others are harsh: the average rating
per tester ranges from 1.8 to 4.75. If the same tester is in both train and test, the model can partly
"recognise" the tester (through age, sex, phone) and look better than it really is on new people.

We checked how much this matters (notebook §6.5). Without feedback, a random split looks about **0.01–0.02
better** than a split by tester. That is small but goes in the expected direction. With feedback there is
no difference. So we keep the split by tester mainly because it matches the real use case (new users).

## 6. Results

Scores on the **held-out test testers** (33 testers, 304 sessions never used for training or tuning):

| Setting | Best model | Macro-F1 | Accuracy | Average error (MAE, in MOS points) |
|---|---|---|---|---|
| Baseline (always predict 4) | — | 0.14 | 0.51 | 0.68 |
| Objective features | XGBoost | 0.41 | 0.54 | 0.53 |
| With feedback | XGBoost | 0.69 | 0.75 | 0.27 |

How to read this:
1. **XGBoost is the best model in both settings** (chosen on cross-validation, not on the test set).
2. **Without feedback, MOS is hard to predict.** Accuracy is only slightly above the baseline. The models
   recognise bad sessions reasonably well, but they cannot tell a 4 from a 5. That difference depends on
   the person rather than on the network.
3. **Buffering time is by far the most useful measured feature**, which matches the literature: stalls are
   what annoys users most. Network type, operator and phone model add very little.
4. **With feedback, performance roughly doubles**, almost entirely thanks to `QoF_audio`.
5. **Distance-based models (kNN, SVC) do worse than tree models.** kNN is the weakest, which makes sense:
   it struggles with a mix of one-hot, ordinal and continuous features. Without feedback, SVC needs an RBF
   kernel with large `C`; with feedback, a simple linear SVC is enough.
6. On the test set the decision tree slightly beats XGBoost without feedback (0.45 vs 0.41). The test set
   is small (only 18 sessions with MOS = 1), so this is within the noise. We stick with the model chosen by
   cross-validation.

Full tables: `results/cv_summary.csv` and `results/test_summary.csv`, or Table 3 in the report.

## 7. Limitations (we should be ready to talk about these)

- Small dataset with few low ratings: test scores are uncertain.
- MOS is ordinal (4 is closer to 5 than to 1), but we treat it as 5 unrelated classes. MAE only partly
  accounts for this.
- No class weighting or resampling, so recall is low on rare classes.
- Personal rating bias of new users cannot be predicted from objective data.
- One campaign, young testers around Paris, 9 phones: the results may not generalise.

## 8. Questions we might get at the defense

- *Why macro-F1 and not accuracy?* Because of the imbalance: 51% accuracy is free.
- *Why not use the QoF columns?* We did, as a separate experiment. They come from the same questionnaire
  as MOS, so they would not be available in practice.
- *Why group by user?* Repeated sessions per tester; we want to generalise to new testers.
- *Why one-hot instead of label encoding?* Phone models have no order, and kNN/SVC use distances.
- *Why is the scaler inside the pipeline?* To avoid leaking validation-fold statistics into training.
- *How does kNN / SVC / a decision tree / XGBoost work?* Each of us should be able to explain all four.
- *Is the test set used for model selection?* No. Selection uses CV only, and the test set is used once at
  the end.
- *How did you use AI?* See the declaration at the end of the report. It must describe what we actually
  did.
